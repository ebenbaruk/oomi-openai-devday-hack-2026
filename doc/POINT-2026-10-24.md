## Spec de ce qui est implémenté

### Architecture retenue

- **Realtime API** d'OpenAI avec `gpt-realtime-2.1-mini`, et **pas GPT-Live**. Raison : GPT-Live décide seul quand parler et n'a ni push-to-talk, ni commit manuel, ni annulation de réponse. La Realtime API permet `turn_detection: null`, `response.create` déclenché par notre serveur, `response.cancel` et `output_audio_buffer.clear`. C'est la seule façon de tenir la promesse « le serveur décide de ce qui est prononcé ».
- **Decisions API** (`gpt-6-luna`) pour le verdict `answer` / `grown_up` / `decline`. Sortie GA le 22 octobre, environ 10× plus rapide que Responses, sortie structurée native avec probabilités.
- Modèles en variables d'environnement : `gpt-realtime-2.1-mini` (voix), `gpt-live-transcribe` (transcription), `gpt-6-luna` (verdict), `omni-moderation-latest` (modération), `gpt-6.1-sol` (Brain, bloc 3), `gpt-image-2.5-flare` (illustrations, bloc 3).

### Un tour vocal, pas à pas

1. **Appui** : le navigateur active la piste micro WebRTC vers OpenAI. Le serveur passe le collier en `listening`.
2. **Relâchement** : le micro est coupé côté navigateur, le serveur envoie `input_audio_buffer.commit`. Un appui de moins de 200 ms est ignoré. Appui maximal 20 s.
3. **Transcription** : OpenAI renvoie la transcription (`gpt-live-transcribe`). Le collier passe en `thinking`.
4. **Contrôle de sécurité** (budget 4 s, sinon repli) :
   - filtre d'entrée : vide, `[noise]`, `(silence)`, sous-titres hallucinés → ignoré, aucune réponse ;
   - modération `omni-moderation-latest` → si signalé, `decline` ;
   - règles déterministes FR/EN (armes, feu, médicaments, adresse, secrets → `decline` ; bébés, mort → `grown_up`) ;
   - verdict Decisions API ; le verdict le plus strict l'emporte entre règles et modèle.
5. **Si `grown_up` ou `decline`** : phrase fixe, jamais générée, lue au client. Les items du tour sont supprimés du contexte OpenAI.
6. **Si `answer`** : `response.create` **hors conversation** (`conversation: "none"`) avec pour seule entrée le texte transcrit. Le modèle vocal n'entend jamais l'audio brut et n'a pas de contexte entre les tours.
7. **Pendant la génération** : le navigateur enregistre la piste audio (`MediaRecorder`) sans la jouer. Le serveur modère le transcript de sortie tous les 120 caractères et annule (`response.cancel` + `output_audio_buffer.clear`) au premier problème.
8. **Fin de génération** : contrôle complet du texte (modération + Decisions « allow / block »). Si OK, `audio.approved`.
9. **Lecture** : le client joue l'enregistrement seulement quand il a **deux feux verts** : approuvé par le serveur et transport terminé. Puis `happy` et retour à `idle`.
10. **Tout échec, timeout ou erreur** → phrase de repli fixe. Jamais de réponse libre.

### Ce que le navigateur peut et ne peut pas faire

- Il n'envoie à OpenAI que l'audio du micro. Toute offre SDP contenant un data channel est refusée par le serveur.
- Il ne parle au serveur qu'avec six événements typés et validés par Zod : `connect`, `press`, `release`, `audio.prepared`, `playback.ended`, `close`.
- Le relâchement est forcé si la fenêtre perd le focus ou si l'onglet est masqué.

### Données

- Tables : `demo_profiles` (âge, langue), `voice_sessions` (une seule active par profil, expiration), `turn_audits` (verdict, statut, durée, horodatage), `rate_limits`.
- **Aucun audio, aucune transcription, aucune conversation en base.** Seulement des métadonnées de tours.
- Un seul profil démo pour le hackathon, identifiant fixe `DEMO_OWNER`. La démo est jouée par des adultes, conformément à la guidance OpenAI sur les moins de 13 ans.

### Sécurité d'accès

- Code d'accès (16 caractères minimum) échangé contre un cookie HMAC `oomi_demo` valable 8 h, `HttpOnly`, `SameSite=Strict`.
- Vérification d'origine sur toutes les routes et sur l'upgrade WebSocket.
- Rate limit 5 tentatives par 15 minutes, en base.

- `npm run eval:live` : les mêmes 11 cas contre les vrais modèles (facturé). Pas encore lancé.
